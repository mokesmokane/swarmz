# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

swarmz is a Tauri 2 desktop app (macOS) that hosts many terminal sessions at once, most of them Claude Code sessions, arranged as a split tree of tab groups. A Rust core owns PTYs and the terminal registry; a React 19 / TypeScript / Tailwind 4 / zustand frontend renders xterm.js panes. The workspace (terminals + layout) persists to `~/.swarmz/workspace.json` and can be shared across Macs on a Tailscale tailnet over plain ssh.

## Commands

```bash
npm install                  # on npm 10.9.x an Arborist bug may require `npx npm@11 install`
npm run tauri dev            # launch the app (runs vite on :1420, then cargo build + window)
npm test                     # frontend unit tests (vitest, one-shot)
npm run test:watch
npx vitest run src/store.test.ts            # single test file
npx vitest run -t "adopts the peer file"    # single test by name
npm run typecheck            # tsc --noEmit
npm run build                # tsc && vite build (frontend only)
npm run build:tool:debug     # build the session holder / swarmz tool
cd src-tauri && cargo test --workspace   # Rust unit tests (app + swarmz-tool)
cd src-tauri && cargo test registry::       # single Rust module
```

There is no linter configured. Vite watches `src/` only and ignores `src-tauri/`; Rust changes need the tauri dev process to rebuild.

## Architecture

### Process split and the IPC contract

- `src-tauri/src/lib.rs` registers every Tauri command. `src/lib/ipc.ts` is the single frontend wrapper over `invoke`/`listen`; nothing else imports `@tauri-apps/api/core`. Adding a command means touching both files (plus `commands.rs`).
- PTY output is emitted as base64 strings on `pty:data:<id>` events, exit as `pty:exit:<id>`. Each PTY spawn gets a generation number so a late exit callback from a restarted terminal cannot clobber the new session (see `take_if_current` in `commands.rs`).
- Rust `TerminalRegistry` (`registry.rs`) is the source of truth for terminal id/name/cwd and enforces unique, shell-safe names. The store mirrors it in `terminals`.
- Rust's `Workspace` struct deliberately knows only `version`, `terminals[].{id,name,cwd,ssh,claude,command}` and `layout`; everything else (`sync`, `machines`, `origin`, unknown fields) rides through `#[serde(flatten)] extra` maps so TS can add fields without Rust changes. TS mirrors this with `TerminalSettings.extra`.

### Frontend state

- `src/store.ts` is one zustand store holding terminals, layout tree, per-terminal settings, ssh/tailscale/sync state, and all actions. Most logic lives here and in `src/lib/`; components are thin.
- `src/lib/layout.ts` is the pure layout tree (`GroupNode` of tabs | `SplitNode` with sizes). All mutations are pure functions returning a normalised tree; `Workbench.tsx` renders it with react-resizable-panels.
- `src/lib/xtermRegistry.ts` owns xterm `Terminal` instances outside React so panes survive re-parenting when tiles move. It imports the store, so the store must not import it: instead it registers `prepare`/`size` onto the store's exported `beforeSpawn` object at module load (imported for side effect in `App.tsx`). The store calls `beforeSpawn.hook(id)` before spawning so event listeners are attached before the first PTY byte.

### Startup lines, not spawn args

Terminals always spawn the user's login shell locally. SSH connections, Claude sessions and custom commands are *typed into the PTY* as lines. `startupSteps()` in `src/lib/workspace.ts` composes them: `via: "local"` lines go straight in; `via: "remote"` lines (e.g. `cd <dir> && claude --resume <id>`) wait until the ssh master is up. Anything interpolated into these lines must go through `shellQuote` and the `validate*`/`isSafe*` guards, and terminal names/aliases are restricted at the registry level for the same reason.

SSH uses OpenSSH multiplexing with a control socket under `~/.swarmz/ssh/%C` (`SSH_OPTS` in TS, `CONTROL_PATH` in `remote.rs`). The first typed ssh line becomes the master (a master-only `ssh -fN` login line, `sshMasterLine`, when the host's tool is not known yet: see Session holders); the core's short-lived commands (`ssh_check`, `ssh_list_dir`, `workspace_pull/push`, `tool_remote_ready`) reuse it with `BatchMode=yes` and never prompt.

Ctrl+V in a connected ssh tile with an image on the local clipboard pushes it as a PNG to `~/.swarmz/paste/` on the remote and types the path (`paste.rs`, `IMAGE_PASTE_KEY` in the registry); text paste is untouched. Panes honour OSC 52 clipboard writes (how Claude Code copies its own selections) via the clipboard plugin, refusing queries; `decodeOsc52` in the registry. Shift+Enter sends LF (`SHIFT_ENTER_SEQUENCE`) because xterm.js sends CR for it and has no kitty keyboard protocol; Claude Code treats LF as a newline, shells as Enter.

### Session holders

Every local tile's shell runs in a detached holder process (`src-tauri/tool`, binary `swarmz-tool`, installed as `~/.swarmz/bin/swarmz`, bundled as `Contents/MacOS/swarmz-tool`). `swarmz hold <tile>` starts or finds it under a per-tile lock (errors: `usage`, `cwd_missing`, `busy`, `failed`); holders run from `/` and drop stale `SSH_*` variables. The app connects to `~/.swarmz/sessions/<tile>.sock` as a viewer (`HolderClient`, `session.rs`), so quitting or relaunching swarmz leaves shells and agents running, closing a tile terminates its holder, and reattaching replays recent output on `pty:replay:<id>` (payload `{data, cols, rows}`: the size it was written at; while it parses, OSC 52, OSC 7 and the resume scan are ignored). `create_terminal` returns `existed`; existing tiles skip the connect card and startup lines. A window joins an existing holder with a 0x0 `Hello`, which applies no size (only when `hold` reports the holder's `build`: holders from older tools would apply 0x0 and get the pane's size instead); the pane resizes to the replay's size and fits afterwards, and once `create_terminal`/`restart_terminal` has resolved (the session is recorded) the store calls `beforeSpawn.claimSize`, which sends the pane's size once, right away if it is laid out or else on its first real fit, even when fitting changed nothing. A replay with history into a pane that already has output resets it first. Once a replay is parsed (its write callback), and again after a remote replay's end marker, the registry asks `terminal_foreground_busy`: if the tile's own shell is in front, `resetTerminalModes` turns off the modes the history left on (Claude's mouse tracking would otherwise type reports into zsh); a running program keeps them, and a failed check changes nothing. `tool` viewers (`swarmz info`, `swarmz close`) get an empty replay and cause no SIGWINCH. `swarmz close <tile>` terminates a holder and prints `{"v":1,"closed":bool}`. `swarmz version` includes a `build` id (set by `tool/build.rs`), which breaks ties between same-version builds for both the local install and remote installs. The sessions lock is never held across `connect` (writes and resizes take it on the main thread).

A tile whose home is another Mac types `ssh … ~/.swarmz/bin/swarmz attach <tile>` when `tool_remote_ready` says the remote tool is usable (the app installs or updates it over the ssh master when the remote is a Darwin machine of the same architecture, never downgrading a newer tool). Attach mode needs a known `selfMachine` and a host that is not this Mac (`attachModeFor`); `attach` itself refuses (code `self`) the tile named by its own `SWARMZ_TERMINAL_ID`. Once the holder answers, `attach` writes `OSC 1337 swarmz-attach;new=<0|1>;end=1`, the replay, then `OSC 1337 swarmz-replay-end`, all under one lock (a failed attach prints only its JSON error): `new=1` types the startup step once (gated by `attachPending`), `new=0` types nothing except an explicitly picked session when the remote shell is idle, and the frontend ignores clipboard and folder escapes until the end marker. Remote folders come from `remote_tile_info`. Closing an ssh tile whose host's tool is ready (or that attached this run) also runs `remote_tile_close` (`swarmz close` over the shared master), best effort and not awaited. Only a definite "not usable" tool check is cached per host, until a failed attach or the next agent install re-checks it; a check that errors is retried on the next Run, which meanwhile uses plain ssh.

Connect logs in before it decides (`runStartupNow`): when the host's tool is unknown and no master is up (`ssh_check`), it types `sshMasterLine(host)` so a password prompt appears once in the tile, polls for the master (`startPolling` mode `master`: the shell is idle after `ssh -fN` backgrounds, so only "no master and shell idle on two polls" is a failed login), then `connectAfterMaster` runs the tool check and `typeConnectLine` types the attach or plain line, which reuse the master. The tile stays `sshConnecting` (and in `startupInFlight`) across the whole step; `masterSteps` tokens make a cancelled step type nothing. A master already up, or a known tool answer, goes straight to `typeConnectLine`. A watchdog (`SSH_WATCHDOG_MS`, 3 s) asks each connected ssh tile's holder for `foregroundBusy` (skipping tiles that are connecting, in `startupInFlight`, polled or in a master step; one check per tile; an error counts for nothing): a definite `false` means the ssh ended, and `markDisconnected` clears `sshConnected`, sets `sshDropped` (the card says Reconnect), re-arms the card with a "Connection to <machine> ended" note (attached tiles: the session is still running there), drops `attachPending` (a `pendingSwitch` stays for the rejoin) and calls `beforeSpawn.resetModes` (`resetTerminalModes` in the registry: mouse, paste, focus, cursor and keypad modes off and the alternate screen left, in the xterm only, never the PTY; it also ends a remote replay). `agentTilesStillLive` uses the same verdict.

The tool is also the phone's whole interface (phone spec §4): `src-tauri/tool/src/commands.rs` has one function per subcommand over small pure modules (`agent` folds `events.log` the same way as `agentState.ts`, checked by the shared `tests/fixtures/agent-status.json`; `transcript` normalises Claude transcripts; `screen` is the holder's `vt100` model behind `Screen` frames; `dialog` reads the permission dialog and Claude's AskUserQuestion dialog (kind `question`: options with descriptions, multi-select boxes, a `submit` answer); `tiles` lists the tiles homed on this Mac; `card` is a tile's conversation title and recap (conversation cards spec: `swarmz card [--tile ID] [--title T] [--recap R] [--user]` merges into the def's `card`, bumps the sync revision and writes the workspace; the tile defaults to `SWARMZ_TERMINAL_ID`; a `user` title survives an agent's recap-only update); `newtile`, `phone`, `gate`). `ls`/`watch` rows carry `title` (the card's, else the session's first prompt folded from `UserPromptSubmit`'s `prompt` by both `agent.rs` and `agentState.ts`), `recap`, `cardAt` and `cardBy`. The holder's screen decides permission state (spec §4.2): a permission dialog on the visible screen means blocked whatever the (asynchronous) hook log says, and no dialog ends a logged permission block; a question dialog blocks with `needs: "question"` and its text as the summary (no hook reports it, so its close just leaves the log's state); `pending`/`answer` use the screen's summary. `restart <tile>` starts whatever is not running: a stopped tile's holder afresh, or, when the holder is up, Claude has exited and the shell is idle (`foregroundBusy: false`), the tile's Claude line typed into that shell resuming its newest conversation (`resume_in_shell`, reply `resumed: true`); a busy shell, a holder that cannot say, or a non-Claude tile is `running`. `send` types the text, then Enter 50 ms later, and re-presses Enter while the screen still shows the text in Claude's input box (`input::still_in_box`: Claude can take an Enter close behind a paste as a newline); `resent` in its reply counts the retries and `submitted: false` says the text is still there after them. With no dialog, a logged permission block reads as working while "esc to interrupt" shows, else idle. A tile's transcript (the hook's path or the guessed one) is followed through Claude's `continued-in` records to the newest file in the same folder (`transcript::resolve_continued`), whose session id `transcript`, `image`, `ls` and `watch` then report; `transcript --after` an id not in it returns the newest page with `reset: true`. Holders that answer `Screen` write `"screen": true` into their metadata (older holders, even ones with a `build`, ignore the frame): without it `output`/`pending`/`answer` refuse with `old_session` and `ls`/`watch` keep the fold. On `Terminate` a holder marks its metadata `terminatingAt` at once, before the shell exits. Tool readers use `workspace::read_from`, which never moves a broken file aside; only writers (`new`, the `__keep-def` helper `new` starts to re-add its def for 30 s when an older copy drops it, stopping once the session is ending) use `load_from`. CLI tests in `src-tauri/tool/tests/cli.rs` run the real binary with `HOME` under `/tmp/szc-*` and `SWARMZ_MACHINE` set (which also skips Tailscale). Phone keys are forced through `swarmz ssh-gate` and limited to tailnet addresses (`from=`).

### The conductor

One tile may act on the others (conductor spec): `workspace.json`'s `conductor` (a tile id) and a pending `conductorClaim` `{tile, title, at}`, both through `extra`. `src-tauri/tool/src/conductor.rs` holds the guard (`allowed`: the desktop and the phone's gate carry no `SWARMZ_TERMINAL_ID` and pass; a tile acts on itself; `transcript`/`image` on another tile are refused for everyone, `output` on another tile is the conductor's alone (`SCREEN_MAX` 200 lines, no `--follow`, capped in `main.rs`); `send`/`ask`/`key`/`answer`/`pending`/`close`/`restart`/`new`/`fleet`/`--on`/`notify` on another tile need the caller to be the conductor; `conductor --set/--deny/--clear` are never a tile's), the claim/set/deny/clear writes (revision bumps), the `ask` and `reply` lines (`[conductor <title>] … — answer with: swarmz reply -- "…"` and `[<title>] …`, cut at 1000), `remote_command` (the tool over the shared ssh master) and `fleet` (local `ls` plus every reachable Mac's, recap and last message cut at 280). `main.rs` calls `guard()` in each dispatch arm and handles `--on <machine>` before dispatch (never for `hold`/`attach`/`ssh-gate`/`phone`/`conductor`); `commands::conductor` tells a claimant the outcome as a typed prompt (`deliver`: locally, or over ssh to its home Mac). `swarmz briefing` prints what the `SessionStart` hook returns (hook script v4 runs it, with the file as a fallback): the common `~/.swarmz/briefing.md` (`swarmz_tool::briefing::BRIEFING`, v3, re-exported by `agents.rs`) with `<name>` filled in, plus the conductor section for the tile's `Role` (top, sub-conductor, or none).

Conductors form a tree (conductor tree spec, as amended): `conductor` is the top, and `conductors` `{tile: {parent, tiles}}` the sub-conductors, each with an explicit list of the tiles put under it (membership is by hand, never by folder). `conductor::Tree::of` keeps the entries whose tile exists and whose chain of parents reaches the top; `owner(tile)` is a sub-conductor's parent, else the live sub-conductor whose `tiles` names it, else the top; `ancestors` walks that. The guard (`allowed(ws, …)`): `send`/`ask`/`key`/`answer`/`pending`/`close`/`restart` need `owner(target) == caller` (a grandchild is refused with "answers to <X>"), `output` needs the caller among `ancestors(target)`, `fleet`/`new`/`--on` any conductor (a sub-conductor's `fleet` is filtered to its descendants, and a tile its `new` starts joins its list), `notify`/`telegram-follow` the top only. `reply` goes to `owner(caller)`. `conductor --assign <tile> --to <conductor>` moves a tile between lists (a tile is in one at most; the top's id takes it back): the user's, or a conductor's for its own tile into a sub-conductor directly under it (`may_assign`). `--claim` records a claim with `sub: true` and `parent` (the claimant's owner) whenever a top exists (`--claim --top` asks to replace the top; with no top a plain claim is for the top), and `--set <tile>` on a sub claim makes the sub-conductor; `--set <tile> --parent P` (make or move one) and `--remove <tile>` (its tiles and children go to its parent) are the user's. Rows and `ls` mark every conductor and carry `conductors`. The desktop mirrors the tree in `src/lib/workspace.ts` (`conductorsOf`, `liveSubs`, `conductorOwner`; store helpers `isConductorTile`, `conductorFor`) and changes it only through `conductor_action` (`set`, `sub`, `assign`, `remove`, `clear`, `deny`): the row's 🎛 opens `ConductorMenu` (Answers to, Make it a conductor here, Make top conductor, Not a conductor, Arrange conductors…), and the header's 🎛 opens `ConductorsPanel` (store `conductorsPanel`), the tree drawn with every tile under its conductor, where dragging a tile onto a conductor assigns it and dragging a conductor re-parents it, with a per-row "Answers to" select and make/unmake buttons. The sidebar's Group by has **Tree** (value `conductor`): `ConductorTree` draws the sidebar's own rows (a `renderRow` prop, so every row behaviour stays) nested under the conductor each answers to (`src/lib/conductorTree.ts`: `buildConductorTree`, conductors first then tiles in workspace order), with conductors that fold (per-Mac `localStorage`, `loadCollapsed`) and say how many are under them and how many need you, and drag and drop on the store's `draggingTerminalId` (the same drag that moves a row into a pane): `dropAction` decides assign, move or nothing, the innermost conductor under the pointer always decides (a refused drop never bubbles to an outer conductor), and changes go through `assignTile`/`setSubConductor`. The desktop carries top-level workspace fields it does not know through every save (`workspaceExtra`, `toWorkspace`'s `extra`), so a newer field is never dropped by an older app.

The desktop holds `conductor`/`conductorClaim` in the store (`loadWorkspace`/`applyWorkspace` read them, `toWorkspace` writes them, `sameWorkspaceContent` compares them; closing the conductor's tile clears the role). Changing the role goes through the tool, not a store edit: `conductorViaTool` flushes any pending save, invokes `conductor_action` (`swarmz conductor --set/--deny/--clear`, which writes the file, bumps the revision and types the outcome into the tiles concerned) and adopts the newer file it left, falling back to the tool's reply. `run_tool_json` scrubs `SWARMZ_TERMINAL_ID` so a dev app launched from a tile is never guarded as that tile. UI: `ConductorBadge` (🎛) on the row, tab and hover card; `ClaimBar` at the top of the sidebar with Approve/Deny (`decideClaim`); a hover 🎛 button on Claude rows (`setConductor`: Make conductor / Not the conductor); **+ → Conductor…** (`conductor_dir` makes `~/.swarmz/conductor` with a CLAUDE.md, the folder picker starts there, `createConductorTerminal` opens a local Claude tile, starts it and sets it). `ls`/`watch` carry `conductor` and `claim` beside the rows (`watch` also emits a `conductor` event on change) and each row a `conductor: true` flag, which the phone shows as a mark in front of titles (`TileRow.badgedTitle`) and as a Home claim card (`Repository.claims`, `approveClaim`/`denyClaim` run `conductor --set/--deny` on the reporting Mac).

Telegram (conductor spec §5) is per Mac: `~/.swarmz/telegram.json` `{token, chatId}` mode 0600 (`swarmz_tool::telegram`: `read`/`write`/`remove`, requests through `curl -K -` with the token in the stdin config, `SWARMZ_TELEGRAM_API` overrides the base URL for tests). `swarmz notify [--tile <id>] -- text` (conductor or user only; `not_configured`/`failed`; the title in bold, HTML-escaped, cut at 4000) and `swarmz telegram-follow [--once]` (long-polls `getUpdates`; only the configured chat counts; `approve`/`deny` answer a pending claim and Telegram hears back, anything else is typed into the conductor as `[telegram] …`, wherever it runs; one JSON line per message with `outcome`). `conductor --claim` also messages the claim when Telegram is set up. The desktop's Notifications panel (🔔, `NotificationsPanel`) reads and writes the file (`telegram_get`/`telegram_set`: an empty token keeps the one set), pushes it to every Mac with a connected tile (`telegram_push`; `install_remote` also syncs it whenever a Mac's hooks are installed) and sends a test through `notify` (`telegram_test`). The follower runs on the conductor's own Mac only: `telegramFollowWanted` (Telegram set up, the conductor a local, non-foreign, running tile) drives `telegram_follow`, which keeps one `Follower` (`src-tauri/src/telegram.rs`: a `swarmz telegram-follow` child, restarted after it ends, killed on stop).

### Workspace persistence and tailnet sync

- Saves are debounced (`SAVE_DEBOUNCE_MS`) and written atomically by Rust (`workspace.rs`, tmp + rename; a corrupt file is moved aside as `workspace.json.broken-*`).
- Sync (`docs/superpowers/specs/2026-09-14-shared-workspace-design.md`) is last-writer-wins on `sync.{revision,updatedAt,updatedBy}` with a machine-name tiebreak (`isNewer`). Every save bumps the revision and pushes the file to every online tailnet peer via `cat`/`mv` over ssh (`sync.rs`); `App.tsx` pulls on load, on focus, every `SYNC_PULL_MS`, and stats the local file every `SYNC_STAT_MS` to detect hand edits.
- `terminals[].origin` records which machine created a terminal. A local terminal whose origin is another machine opens here as an ssh terminal to that machine in the same cwd (`openingFor`), and is written back as a local def of its origin (`toWorkspace` uses `settings.foreign`). A machine's first sync merges rather than adopts (`mergeForFirstSync`).
- A file the tool wrote on this Mac (`swarmz card`, `conductor`, `new`: `sync.updatedBy` is this machine) is adopted by the stat poll and then pushed to the peers at once (`announceLocalWrite`); otherwise they would learn of it only on their next pull, and any save they made before that would start from the old revision and overwrite it.
- The conductor fields (`conductor`, `conductors`, `conductorClaim`) carry their own stamp, `conductorAt`, set by every tool write to them (`conductor::touched`) and by the desktop when closing a tile changes them. The newer set wins whatever the file's revision says: `applyWorkspace` keeps the store's roles when they are newer than the adopted file's (and `adopt`'s drift check saves them back out), `runSave` first takes newer roles from the file on disk (`workspace_roles`, `takeNewerRolesFromDisk`), and `conductorViaTool` applies the tool's reply before adopting. Without this, a Mac saving every few seconds from an older copy wrote the old roles straight back over a role change.
- Adoption must converge: comparisons use `sameWorkspaceContent` (order-insensitive, ignores `sync`) so two machines never ping-pong revisions over terminal order. Keep any new comparison order-insensitive.
- Tailscale is only used for discovery: `tailscale status --json` via the CLI (`tailscale.rs`), short MagicDNS name as the machine key. Login is plain ssh over the tailnet.

### Agent state

Claude Code lifecycle hooks (`SessionStart`, `UserPromptSubmit`, `Stop`, `StopFailure`, `Notification`, `SessionEnd`, `PermissionRequest`, `PostToolUse`; installed once per machine into `~/.claude/settings.json`, script at `~/.swarmz/hooks/claude.sh`, version 2; every event but `SessionEnd` and `PostToolUse` is async) append one line per event to `~/.swarmz/agents/events.log` on the machine Claude runs on. `agents.rs` tails that file locally and over the shared ssh socket for each tailnet machine with a connected tile, emitting `agent:event`. `src/lib/agentState.ts` is the pure reducer (offline / working / idle / blocked, plus `unseen`), with its dot colours in `STATUS_COLORS`; the store owns watcher lifecycle, replay rules (local events from before launch are buffered until the first `loadWorkspace` has opened its tiles, because the watcher replays the log before any holder answers; they then apply in order, but only to tiles whose `create_terminal` returned `existed: true` and only from that holder's `startedAt` on; remote history always applies) and the `claude.started` flip on the first `UserPromptSubmit`. Remote claude lines carry `SWARMZ_TERMINAL_ID=<id>` because the remote shell does not inherit the local env. Hook script version 3 also returns `~/.swarmz/briefing.md` (with `<name>` filled in; `BRIEFING` in `agents.rs`, versioned by its first-line HTML comment, installed locally and on tailnet Macs, left alone once a user removes that line) as `SessionStart` additional context, which is how every session in a tile learns to keep its card with `swarmz card` (the recap is a `/recap`-shaped status line under 280 characters, never a changelog; a fallback title skips slash commands and harness-injected prompts starting with `<`); `SessionStart` runs synchronously for that, and the install adds the two `Bash(… swarmz card:*)` allow rules to `permissions.allow`.

### Phone app

`android/` is a separate Kotlin/Jetpack Compose app (`dev.swarmz.phone`, sub-project 3 of `docs/superpowers/specs/2026-09-16-swarmz-phone-design.md`) that drives terminals from a phone; it shares no build with the Tauri app and is not touched by any `npm`/`cargo` command above. Packages under `android/app/src/main/java/dev/swarmz/phone/`: `data` (repository, settings), `keys` (Ed25519 phone key, Android-Keystore-sealed), `link` (per-Mac connection, watch/follow streams), `pairing`, `proto` (the tool's JSON models and command/reply codecs), `ssh` (sshj wrapper), `state` (pure reducers), `ui` (Compose screens and their view models: `AppViewModel`, `TileController`, `NewSessionModel`). A long press on a tile row or Home chip opens `TileMenu` (Open, and Stop behind a confirm or Start), wired to `AppViewModel.stopTile` (`close`) and `startTile` (`restart`), with failures in `tileNotice`. The phone never talks to the Rust core directly: it speaks the same `swarmz` tool JSON described above (§4 of the phone design spec) over ssh, one word per `Cmd` argument, single-quoted; the ssh gate on each Mac (`ssh-gate`, forced command from `phone add`) only allows `swarmz <sub>` for the subcommands the phone needs, so a phone key can run tile commands but not `hold`, `attach` or the internal ones.

Tests run with `./gradlew :app:testDebugUnitTest` from `android/` (a single package: `--tests 'dev.swarmz.phone.state.*'`); they are JVM-only (no emulator), using Robolectric for Compose UI tests and an embedded Apache MINA sshd for ssh, and never touch a real `~/.swarmz`, `~/.ssh` or host. "Unfolded" (list beside the open tile) means a width of at least 600 dp, checked with `BoxWithConstraints` rather than material3-adaptive; the view model, not any screen, holds the open tile, composer draft and scroll position so folding and unfolding keeps them. See `android/README.md` for the toolchain, build, release signing and pairing steps.

### Phone attachments

`swarmz upload --name <name> --size <bytes>` (`src-tauri/tool/src/upload.rs`) reads exactly that many bytes from stdin into `~/.swarmz/paste` (the desktop's Ctrl+V folder) under a stamped, sanitised name, temp file first and moved into place only at full size, 25 MiB cap, and prints the path; `prune` sweeps paste files older than 7 days. It is the one gated command that reads stdin: the gate `exec`s the tool, so the ssh channel's stdin is its stdin. On the phone, `SshConnection.exec(command, input, onProgress)` writes the bytes to the channel on its own thread, `MacLink.execInput` holds a slot for the upload, `Repository.upload` refuses an offline Mac, and `TileController.attach` queues uploads one at a time (`attachments`, chips above the composer with progress, retry and remove) and inserts the returned path into the draft at the cursor. `readPicked` in `ui/tile/Attachments.kt` reads a content URI (an image over the cap is re-encoded smaller). The activity is a share target (`ShareIntent.kt`): `AppViewModel.share` applies to the open tile or waits on Home ("Choose a tile for …") for the next `open`.

### File viewing

Panes get an xterm link provider (`src/lib/paneLinkProvider.ts`, registered in `createEntry`; the pure matcher is `src/lib/paneLinks.ts`: `findPaths`, `findUrls`, `resolvePath`) so a hovered file path or URL underlines and a click opens it (file viewing spec). A path opens `FileViewer` (mounted in `App.tsx`, state `fileView` in the store via `openFile`/`closeFile`): `read_file(host, path)` reads it from this disk or, for a connected ssh tile, over the ssh master (`files.rs`: `remote_read_command` prints a kind line, the size and base64 of up to `VIEW_MAX` 2 MiB; `parse_remote`), classifying text by content and images by extension. The viewer colours text line by line with highlight.js (`HIGHLIGHT_LANGUAGES`), marks and scrolls to the linked line, renders markdown through marked and DOMPurify with a Raw toggle, shows images inline and a note for binaries. Relative paths resolve against the tile's folder (`tileFolder`: the ssh cwd, the foreign cwd or the terminal's) and `~` is left for the core, which expands it with the home of the Mac the shell runs on. `open_url` opens `http`, `https` and `file` URLs with macOS `open`. A folder reads as `kind: "dir"` (local `read_dir`, remote `ls -1Ap`), listed in the viewer with `..` and each entry clickable. **Open** is `open_path` (`open_local`: `/usr/bin/open`, `-R` for **Reveal**, local only); a remote file is first copied with `scp` over the master to `~/.swarmz/remote/<host>/<path>` (`fetch_remote`, `scp_command`) and the copy opens. **Open in VS Code** shows when `code_binary` finds `code` (PATH, then the usual places, once per run): `code --goto path:line` here, `code --remote ssh-remote+<host> --goto …` for an ssh tile, with `~` resolved from the remote `$HOME` (`open_in_code`, `code_args`).

### Breakout windows

A tile can live in its own window (breakout windows spec). It is a *view, not a move*: the shared layout keeps the tile, `store.breakouts` (per Mac, persisted with window bounds in `localStorage` by `src/lib/breakouts.ts`) hides its pane behind a placeholder in `TabGroup`, and `breakoutTerminal`/`returnTerminal`/`restoreBreakouts` go through `breakoutHooks`, which `src/lib/breakoutWindows.ts` fills in (imported for its side effects in `App.tsx`; tests never load it). That module creates the `tile-<id>` `WebviewWindow` on `breakout.html` (a second Vite input rendering `BreakoutApp`), pushes a `TileState` snapshot on every relevant store change (`tile:state:<id>`), answers `breakout:hello`, acts on `breakout:action` (return, restart, focus-main) and returns the tile when the window is destroyed. The core gives each breakout window its own holder viewer (`open_view`: a sizeless Hello, replay emitted to that window alone; `close_view`; viewers dropped on window destroy), and `write_terminal`/`resize_terminal` use the calling window's viewer when it has one. Drag-out: `endTabDrag` breaks a tab out when its drag ends with no drop and the pointer is outside the main window's bounds. Capabilities: `capabilities/breakout.json` covers `tile-*` windows.

### Sidebar list

Rows are built from `rowInfo` in `src/lib/sidebarGroups.ts` (sidebar groups spec): a machine chip (the Tailscale name, alias in the tooltip, colour, hollow when a remote is offline), the folder basename, a status word (`needs you`, `working`, `idle`, `stopped`, `exited N`) and the last activity (`agentState.since`, else the newest session's `lastActiveAt`) as `now`/`3m`/`2h`/`1d`, ticking every 30 s (`useNow`). The "Group by" control (Workspace, Machine, Status, Folder; `groupRows`) is a per-machine `localStorage` preference; grouped lists sort each group by activity, newest first. Rows are the same component in every grouping, so drag, rename, title edit, history and the hover card do not change.

### Sidebar width

The sidebar is resized by dragging the 4 px handle between it and the workbench (`App.tsx`), double-click resets it; the width is a per-machine preference in `localStorage` (`src/lib/sidebarWidth.ts`, clamped 180–640, default 256), never part of the shared workspace.

### Conversation cards

A tile's `settings.card` (`src/lib/card.ts`: `{title?, recap?, updatedAt, by: "agent" | "user"}`) is read from and written to its workspace entry (`card` is a known def key, and part of `sameWorkspaceContent`). The sidebar row and tab show `displayTitle`: the card's title, else the agent state's `title` (the session's first prompt, set by `applyAgentEvent` from the event's `prompt`), else the name, which then moves to the second line. Hovering a row for `HOVER_CARD_MS` opens `HoverCard` (recap, else the first prompt, else "No recap yet"); double-clicking the title edits it as the user's (`setCardTitle`, `withUserTitle`), and the rest of the row still renames. The phone shows `TileRow.shownTitle` in rows, chips and the tile header, whose tap opens the recap dialog with an **Edit title** that runs `card --user`.

### Folder tracking and session history

A tile's saved folder is live: local tiles ask their holder for the shell's cwd (`terminal_cwd`, answered from the holder's `Info`, as is `terminal_foreground_busy`) 300 ms after Enter and every 5 s while the window is focused (connected ssh tiles with a ready tool ask the remote holder via `remote_tile_info` instead), and every tile honours the OSC 7 directory escape, for ssh and foreign tiles only once ssh is connected so a local prompt cannot overwrite the remote folder; a `SessionStart` hook event's cwd is the session's project folder and is applied too, but a prompt's cwd is not: Claude Code reports its own Bash shell's folder there, which moves as Claude `cd`s, and following it made the folder flip against the holder's (re-arming the connect card and bumping the workspace on every Mac). Changes route through `setTerminalCwd` (registry for local, `settings.ssh.cwd` for ssh, `settings.foreign.cwd` for foreign locals). `src/lib/sessions.ts` keeps each tile's `sessions` list (newest first, max 20); `applyAgentEvent` adopts the live session on SessionStart, `selectSession` goes back to one (moving a local shell with `cd` first), and a `--resume` that Claude reports as gone removes the record.

## Tests

- Store and lib tests run in node; component tests need `// @vitest-environment jsdom` as the first line. Every frontend test mocks `./lib/ipc` (and `@tauri-apps/api/path`, `@tauri-apps/plugin-dialog` where used) with `vi.mock`; look at `src/store.test.ts` for the reusable fake registry pattern.
- `src/store.test.ts` is the main spec for sync/adoption behaviour; new sync rules belong there.
- Rust modules carry their own `#[cfg(test)]` blocks; `workspace.rs` tests use per-process temp dirs.

## Docs and workflow

Design specs live in `docs/superpowers/specs/` and implementation plans in `docs/superpowers/plans/`, dated `YYYY-MM-DD-<topic>.md`. Later specs amend earlier ones and say so in their header; check the newest spec for a feature before changing behaviour. Commit messages follow `type(scope): summary` (e.g. `fix(ui): …`, `feat(core): …`).

`docs/RELEASING.md` is how a release is cut: `npm run version -- <x.y.z>` sets the one version in `package.json`, `src-tauri/tauri.conf.json` and `android/app/build.gradle.kts`, and pushing a `v*` tag makes `.github/workflows/release.yml` build, sign, notarise and draft it. Never build or bundle the desktop app locally; CI does that.
